# code-comments-cleanup

Agents leave a lot of documentation behind. Some of it is useful; much of it narrates the plan they
followed, quotes the conversation, lists today's callers, or restates the line below it. This skill
reviews **every comment in every file changed on the branch** and leaves behind only documentation
that earns its place.

## When to use

- When the user asks to *clean up comments*, *review the docs/comments on this branch*, or *tidy TSDoc/JSDoc*
- When the user asks to remove *agent-written*, *AI-generated*, or *slop* comments
- As a final pass before opening a PR, after an agent has written or refactored code

## Instructions

### 1. Resolve the base ref and collect the changed files

If the user named a base branch or ref in their request (e.g. *"clean up the comments against
develop"*), use it as `BASE_REF`. Otherwise derive the repository's default branch:

```bash
if [ -z "$BASE_REF" ]; then
  DEFAULT_BRANCH=$(git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null | sed 's|^origin/||')
  DEFAULT_BRANCH="${DEFAULT_BRANCH:-main}"
  git fetch origin "$DEFAULT_BRANCH" --quiet 2>/dev/null
  BASE_REF="origin/$DEFAULT_BRANCH"
fi
MERGE_BASE=$(git merge-base "$BASE_REF" HEAD)
```

Collect committed, staged, unstaged and untracked files in one set:

```bash
{
  git diff --name-only --diff-filter=ACMR "$MERGE_BASE" HEAD   # committed on this branch
  git diff --name-only --diff-filter=ACMR HEAD                 # staged + working tree
  git ls-files --others --exclude-standard                     # untracked
} | sort -u
```

**Guard:** if the resulting set is empty, **stop immediately** and tell the user:
> "No files changed against `<base-ref>` — nothing to review."

Do **not** guard on being on the default branch: an agent that just wrote comment slop directly on
`main` is exactly a case this skill should handle.

### 2. Drop files that must not be rewritten

Remove from the set:

- Generated or build output: `dist/`, `build/`, `out/`, `coverage/`, `node_modules/`, `.next/`, `*.min.*`
- Vendored or third-party code: `vendor/`, `third_party/`
- Generated type declarations and snapshots: generated `*.d.ts`, `__snapshots__/`, `*.snap`
- Lockfiles and machine-written data: `*.lock`, `yarn.lock`, `package-lock.json`, `*.generated.*`, `*.gen.*`
- Test fixtures where the comment text *is* the data under test: `__fixtures__/`, `fixtures/`, and any
  test whose assertions reference comment content
- Any file whose first lines carry a codegen banner:

```bash
head -5 "$file" | grep -qiE '@generated|do not edit|auto-generated|autogenerated'
```

Keep only files that can hold comments (source, config with comment syntax, docs embedded in code).
Mention skipped-but-suspicious files in the final summary instead of editing them.

### 3. Read each file and locate its comments

Review the **whole file**, not only the diff hunks. The most common agent artifact is a function body
that was rewritten while the stale doc block above it stayed untouched — a diff-line filter misses
exactly that comment.

To locate candidates quickly in large files:

```bash
grep -nE '^[[:space:]]*(//|/\*|\*|#|<!--)' "$file"
```

Treat that output as a *hint list only*: it misses trailing comments (`foo(); // why`) and matches
comment-looking text inside strings, template literals and URLs. Always confirm against the real file
content.

Process the files **one at a time** — read, classify, edit, move on — so a large branch cannot
exhaust context halfway through and leave the summary silently incomplete. If the set exceeds ~30
files, report the count first and ask the user whether to narrow the scope before starting.

**Never judge a comment on its own.** Read the symbol it documents first — whether a comment adds
value is a statement about the code below it, not about the sentence itself.

### 4. Classify every comment: KEEP / REWRITE / DELETE

Apply the [rewriting rules](#rewriting-rules) below, in order:

1. Is it a [protected comment](#comments-that-must-never-be-touched)? → **KEEP**, untouched, byte for byte.
2. Does it state something a competent reader cannot get from the code in two seconds? If no → **DELETE**.
3. Does it violate a rule but still carry a real fact (a constraint, a failure mode, a reason)? →
   **REWRITE**, keeping the fact and dropping everything else.
4. Otherwise → **KEEP**.

When torn between REWRITE and DELETE for a comment that holds one genuine fact, rewrite it down to
that fact. When torn between KEEP and DELETE, and the comment only paraphrases the code, delete it.

### 5. Apply the edits

Edit comments in place. Preserve the surrounding style: `//` stays `//`, `/** … */` stays a doc block,
indentation and the file's existing doc conventions are unchanged. Never reflow or re-indent nearby code.

**Comment-only edits.** This pass must not change a single line of executable code — no renames, no
reordering, no formatting, no "while I'm here" fixes. If you spot a real bug, report it in the summary
and leave the code alone.

### 6. Verify the result

**(a) Prove the pass was comment-only.** Inspect your own diff and confirm every added/removed line is
a comment line or blank:

```bash
git diff -U0 -- <files you touched> | grep -E '^[+-]' | grep -vE '^(\+\+\+|---)'
```

Every line in that output must be a comment or an empty line. If any executable line appears, revert it.
Untracked files do not show up in `git diff` — for those, re-read the file and confirm the same property
by eye.

**(b) Typecheck.** Comment edits *can* break a build: JSDoc `@type` / `@satisfies` annotations are
load-bearing in `.js` files, and an `@ts-expect-error` errors both when removed (the real error
resurfaces) and when left on a line that no longer errors. Run the project's typecheck if one exists:

```bash
jq -r '.scripts | keys[]' package.json 2>/dev/null | grep -iE 'typecheck|tsc|lint'
```

Run the matching script and fix any breakage caused by this pass before reporting.

### 7. Report a summary

Print a Markdown table of changes only (unchanged comments are not listed):

| # | File & Line | Symbol | Action | Reason |
|---|-------------|--------|--------|--------|
| 1 | `src/cart.ts:42` | `applyDiscount` | ✍️ Rewritten | Listed callers and restated the signature |
| 2 | `src/cart.ts:88` | `toCents` | ✂️ Deleted | Restated a one-line conversion |

Then add:

- **Deleted comments** — the full original text of every deletion, so the reviewer can eyeball what
  is gone without reading the diff.
- **Candidates for documentation** — symbols with non-obvious failure modes, ordering constraints or
  side effects that currently have *no* doc. List them; do not write the docs (see
  [Do not author new documentation](#do-not-author-new-documentation)).
- **Skipped files** — anything dropped in step 2 that looked like it may hold hand-written comments.

## Rewriting rules

### R1 — Short, plain, direct

A comment nobody reads is worth nothing, and length is the main reason comments go unread. One or two
lines. No preamble, no ceremony, no restating the signature in prose.

```ts
// ❌
/**
 * This function is responsible for taking the provided user identifier and then
 * performing a lookup operation against the database in order to retrieve the
 * corresponding user record, which it will subsequently return to the caller.
 */

// ✅
/** Loads a user by id. Returns `null` when the row is missing. */
```

### R2 — Never mention consumers

Callers change; the comment does not. Document what the symbol *is*, never who happens to use it today.

```ts
// ❌
/** Formats a price. Used by CartSummary, CheckoutHeader and the PDF invoice renderer. */

// ✅
/** Formats a price in the currency's minor units, rounding half up. */
```

### R3 — No plan or agreement provenance

A comment must stand on its own for a reader who knows nothing of the work that produced it. Strip
every reference to steps, phases, migrations-in-progress and "for now" scaffolding that only made
sense inside a plan.

```ts
// ❌
// Step 3 of the refactor plan: temporary adapter until phase 2 lands.

// ✅  (either the constraint is real and stated as a fact…)
// Bridges the legacy snake_case payload; remove once the v2 endpoint is the only producer.

// ✅  (…or, if it says nothing durable, delete the comment)
```

### R4 — No conversation residue

Nothing from the exchange with the user belongs in the source: no "as the user asked", "as requested",
"the user explicitly wanted this", no hedging about who is to blame for a decision, and no passive
aggression.

```ts
// ❌
// The user insisted on skipping validation here, against my recommendation.

// ✅
// Input is already validated by the route schema; re-validating here doubled p99 latency.

// ✅  (no technical reason to record → delete the comment)
```

A decision that looks wrong at first glance may still deserve a line — but that line explains the
*engineering* reason, never the negotiation.

### R5 — Document the non-obvious, not the obvious

A trivial symbol needs no doc. Where a symbol *does* deserve one, spend the words on what reading the
happy path will not reveal: thrown errors, `null`/`undefined` results, mutation of arguments, ordering
or initialisation requirements, retries, caching, concurrency, silent fallbacks, units and time zones.

```ts
// ❌
/** Returns the sum of a and b. */
function add(a: number, b: number) { return a + b; }

// ✅ — no comment at all

// ❌
/** Parses the config file and returns the config. */

// ✅
/** Throws `ConfigError` on malformed YAML; a missing file yields the defaults. */
```

### R6 — No value → delete, don't shrink

Shrinking a worthless comment leaves a shorter worthless comment. If a comment survives only because
deleting things feels rude, delete it.

```ts
// ❌
// Loop over the items
for (const item of items) {

// ✅ — nothing
for (const item of items) {

// ❌ — a doc block that names the thing it sits on
class User {
  /** Constructor. */
  constructor(/** The user's name. */ public userName: string) {}
}

// ✅ — nothing
class User {
  constructor(public userName: string) {}
}
```

## Comments that must never be touched

These read like noise to a cleanup pass and are load-bearing. Keep them exactly as they are, including
their position — `eslint-disable-next-line` and friends are positional, so **never reorder or relocate
a comment**.

- Linter and compiler directives: `eslint-disable*`, `biome-ignore`, `prettier-ignore`, `@ts-expect-error`,
  `@ts-ignore`, `@ts-nocheck`, `@ts-check`, `istanbul ignore`, `c8 ignore`, `v8 ignore`, `NOSONAR`
- Type-carrying JSDoc in `.js`/`.mjs` files: `@type`, `@typedef`, `@param`, `@returns`, `@template`,
  `@satisfies`, `@implements`
- Triple-slash directives: `/// <reference … />`
- Compiler and bundler pragmas: `/* @__PURE__ */`, `/* webpackChunkName: … */`, `/* webpackIgnore: true */`,
  `/* @vite-ignore */`, `@jsx`, `@jsxImportSource`, `"use client"`-adjacent pragmas
- API-surface tags that tooling and IDEs render: `@deprecated`, `@internal`, `@public`, `@alpha`, `@beta`,
  `@packageDocumentation`, `@see`, `@example`
- Licence and copyright headers, SPDX identifiers, and codegen banners
- Editor folding markers: `//#region`, `//#endregion`
- Localisation/extraction comments consumed by a toolchain (e.g. `// i18n-extract`, `/* i18n: … */`)

A `@deprecated` or `@example` block may still have its **prose** tightened under R1; the tag itself stays.

Beyond directives, some short comments look like slop and are not. Keep them:

```ts
// ✅ KEEP — records a non-obvious workaround with a trail to follow
// Safari 17 fires `resize` before layout settles; the rAF hop avoids a 0-height read. (WK-243081)

// ✅ KEEP — a real ordering constraint the code cannot express
// Must run before `initAnalytics()`: the consent flag is read once at init.

// ✅ KEEP — the surprising empty case is the whole point
// An empty `ids` list means "match everything", not "match nothing".
```

The test is always the same: **does a reader lose a fact if this line disappears?**

## Do not author new documentation

This skill *cleans*, it does not document. While rewriting an existing comment you may expand it to
cover a throw, a nullable result or a side effect you can see in the code — that is still the same
comment, made accurate. But do not add a doc block to a symbol that has none, and do not add `@param`
or `@returns` rows a file's convention does not already use. Undocumented symbols that deserve
attention go in the summary as candidates, for the user to decide.

## Key constraints

- **Comments only.** Never modify executable code, imports, formatting or file names in this pass.
  Verify it in step 6.
- **Never reorder or move comments** — directive comments bind to the line below them.
- Never touch the protected comments listed above, generated files, snapshots, or fixtures whose
  comment text is asserted by tests.
- Never invent a fact. If a comment claims something you cannot confirm in the code, drop the claim —
  do not rewrite it into a new, equally unverified claim.
- Prefer deletion over decoration: fewer, sharper comments is the goal, not uniformly documented code.
- Keep the file's existing language and comment style; do not translate or convert `//` blocks into
  doc blocks.
- Never expose secrets, credentials, internal URLs or PII in a rewritten comment, even if the original
  contained them — report those separately instead.
- If the typecheck in step 6 fails because of this pass, fix or revert the offending comment before
  reporting success.
